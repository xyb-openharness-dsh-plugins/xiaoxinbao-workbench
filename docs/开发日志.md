## 2026-10-15 · 0.3.11（根因定位与真实 GUI 验收通过）

### 单元 13：定位并修复渲染期 `Workbench registration requires a client package entry name.`

- **判错并撤回**：先怀疑包名 / `__ModuleLoader__.load({ id })` / `cordis.patch.yml` 的 `name` / peerDependencies 范围 / `.dsh-market` 的 disabled 列表 / generation 投影标记，逐项核对均与本包无关；又怀疑服务端入口导出缺失（历史 SyntaxError）和 generation 按 id 缓存（同版本复用旧产物），两轮修复后报错依旧，证明这些都不是根因。
- **决定性线索**：`~/Library/Logs/DSH Desktop/harness.log` 全量检索 `entry name` **零命中**，最新启动段检索 `cancer` 零命中 → 报错发生在**浏览器渲染进程**，不写服务端日志。
- **根因**：宿主 `dsh-desktop-workbenches` 客户端的 `sourcePackage()` 读的是 **service 实例自身绑定**的 Cordis fiber 名称（`this.ctx.fiber?.entry?.options?.name`）。注册时工作台通过 `ctx.desktopWorkbenches` 这个追踪代理访问服务，`.ctx` 被重绑到调用方 fiber，所以注册成功（`desktop-storage.json` 的 `known-providers.v1` 里确实留下了本项目条目）；但宿主渲染业务面板时传的是**原始 service 实例**（`h(item.Component, { service, entry, active, conversation })`），其 `this.ctx` 固定指向宿主 fiber，名称等于 `dsh-desktop-workbenches`，命中守卫抛错，整页渲染失败。用户看到的英文原文来自**本插件自己的 ErrorBoundary**，这本身即是"错误由我方组件抛出"的证据。
- **修复**（`src/client.js`）：把 `ownsSession` 包一层 try/catch，并按宿主渲染路径自身使用的判据回退：`state.sessionBindings[id] === entry.id`。**没有**退化成 `catch { return false }`，否则历史会话永远不被归属。未使用 `ensureSession()`，无需额外容错。
- **验证**：用宿主 app.asar 内的真实 `react`/`react-dom` + `jsdom` 渲染安装副本，mock 的 `ownsSession()` 故意抛同一个错误 —— 4 个调用点抛错全部被吸收，主界面无错误态，历史会话仍被正确归属，无 React key 警告。

## 2026-10-15 · 0.3.12（陪伴提示词重写）

### 单元 16：用户实测反馈「沟通缺乏同理心，没有起到基本心理支持作用」

- **现象**：在「亲戚吐槽」场景里，模型还没听完就给「怎么挡回去」的话术、追问了「他是什么时候走的」这类创伤细节、并长篇分析这段关系。用户给出的完整对话记录还包含一处正确的自我纠正（模型承认"是我在做咨询，不是在当一个人"），说明问题不在模型能力上限，而在提示词没有约束住默认助手行为。
